## 1. 문제와 계획

### 1.1 관찰된 실패 두 가지

| | 증상 | 원인 |
|---|---|---|
| A | 다 지웠는데 계속 닦는다 | 종료 조건이 "시간"이지 "상태"가 아님 |
| B | 덜 지운 부분을 끝내 안 닦는다 | 같은 원인 + 부분 지워진 상태가 학습 분포 밖 |

둘은 같은 원인의 양면이다. 학습 데이터가 전부 "깨끗한 보드에서 시작 → 다 지울 때까지
약 24초(중앙값 720프레임)"라, 정책이 습득한 것은 닫힌 루프가 아니라 **지속시간 prior**다.
시간이 남으면 계속 닦고, 시간이 다 되면 남아 있어도 멈춘다.

### 1.2 계획

1. **판정 기능** — 지금까지 얼마나 지웠는지를 룰베이스로 측정.
   이게 있어야 조기 복귀(A)든 추가 지시(B)든 가능하다.
2. **게이트** — 판정 결과로 시도를 끝내거나 재시도시킨다. SmolVLA를 건드리지 않는다.
3. **HIL 개입** — 정책이 못 하는 상황에서 사람이 리더암으로 보조.
4. **개입 데이터로 추가 학습** — 3에서 나온 궤적으로 B를 근본 해결.

이 문서는 1~3을 다루고 4는 전제 조건만 정리한다.

## 2. 선행연구의 판정 방식 (요약)

상세는 `docs/erase_metric_survey.md`. 요점만:

- **로봇 조작은 거의 전부 이진 0/1.** RL-100(Sci. Robot. 2026)은 8개 task 중 7개를
  사람이 키보드로 +1/0을 매기고, ConRFT(RSS 2025)와 LeRobot HIL-SERL은 학습된
  binary classifier(2-class, threshold 0.5)를 쓴다. 연속값을 쓰는 예외는 dense shaped
  reward가 있을 때뿐이다(RL-100의 push-T = 모션캡처 pose 오차).
- **청소 로봇·시설 위생은 연속 %.** wiped area % = (초기 − 미청소)/초기,
  잔여 분진 제거율 94.7%, 스크러빙 99.7% 등.
  ⚠️ 단 CleanUpBench 등의 **Coverage Ratio는 "지나간 면적"이지 "지운 면적"이 아니다.**
- **치과·섬유는 연속 %가 표준이고 검증 방법까지 확립돼 있다.** plaque planimetry는
  % coverage area를 before/after 2장으로 재고 ICC 0.930 / Bland-Altman으로 신뢰도를
  보고한다. 섬유는 CIELAB ΔE(1 ΔE ≈ 사람이 겨우 구분하는 차이).

**우리는 연속 %를 재고, 임계로 이진화해서 성공 판정에 쓴다.** 이진만으로는
"덜 지움"과 "전혀 안 지움"을 구분 못 해 재시도 여부밖에 결정할 수 없다.
연속값이 있어야 "얼마나 남았는지"를 알고 추가 지시가 가능하다.
성공/실패 자체는 선행연구와 비교 가능하도록 이진으로 보고한다.

## 2.5 우리는 % 를 어떻게 재는가

### 정의

도형 하나에 대해:

```
ink(frame, bbox) = bbox 안에서 (gray < ink_thr) 인 픽셀의 비율
ink_thr          = white × dark_ratio          (white = 보드 흰 영역 밝기, dark_ratio=0.72)

erased_frac = (ink_before − ink_after) / ink_before      [0, 1]로 클립
```

`ink_before`는 시도 전 park 프레임, `ink_after`는 시도 후 park 프레임에서 잰다.
**치과 planimetry의 before/after 2장 비교와 정확히 같은 구조**이고, 분모가 초기
잉크량이므로 도형 크기·획 굵기가 달라도 정규화된다.

### 왜 면적 비율인가 (ΔE가 아니라)

ΔE는 색 변화의 크기를 재고, 면적 비율은 "몇 픽셀이 잉크에서 배경으로 넘어갔나"를 잰다.
우리 과제는 **잉크가 옅어지는 게 아니라 없어지는** 문제라 이진 마스크 면적이 자연스럽다.
다만 면적 metric은 **옅게 번져 남은 잉크에 관대하다** — 마카가 문질러져 흐려졌지만
남아 있으면 임계 위로 올라가 "지워졌다"고 잡힐 수 있다.
→ ΔE(또는 ΔL\*)를 **보조 지표**로 같이 보고하면 이 사각을 덮는다. §9 미해결 항목.

### 이미 결정된 구현 사항 (전부 실제 버그였음)

1. **처음/마지막 유효 관측값으로 계산한다.** envelope(running-min)을 쓰면 중간에
   스쳐간 그림자 같은 일시적 저점을 붙잡아 distractor 노이즈가 4배로 부푼다
   (0.009 → 0.044, 분리 110배 → 22배). envelope은 진행도 곡선 전용.
2. **채도 필터(나무 지우개 블록 제거)는 contour 병합 전에** 적용. 나중에 하면
   블록이 옆 도형과 한 덩어리가 된다.
3. **bbox 근접 병합(30px) 후에 분류.** 손그림은 획이 끊겨 contour가 조각나므로,
   병합 전에 분류하면 삼각형을 원으로 오분류한다.
4. **같은 종류 도형이 여러 개면 dict 키를 `label#i`로 분리.** 키가 충돌하면
   시계열이 이어붙어 `frames_to_90pct`가 영상 길이를 넘는다.

### 도형이 여러 개일 때의 집계

```
target_erased      = min(같은 label 도형들의 erased_frac)     # 보수적
max_distractor     = max(다른 label 도형들의 erased_frac)
성공 = target_erased ≥ 0.9  AND  max_distractor ≤ 0.15
```

target에 `min`을 쓰는 이유: 삼각형이 두 개인데 하나만 지웠으면 실패로 봐야 한다.
`max_distractor`는 **language grounding 실패율**로 그대로 쓸 수 있다 —
엉뚱한 도형을 건드렸는지를 재는 값이다.

### 임계값의 근거

- 성공 임계 0.9: target 평균이 0.987이므로 여유가 크다.
- distractor 임계 0.15: 노이즈 플로어가 p95 0.037이므로 **매우 헐겁다.**
  0.10까지 조일 여지가 있고, 민감도 분석을 표 한 줄로 낼 수 있다(§8).

### 연속값이 있어서 추가로 낼 수 있는 것

- **잔여량 분포** — 실패 에피소드가 0.85인지 0.2인지. 이진 판정 연구는 못 내는 표.
- **진행도 곡선** — `dense_progress()`로 시각화 전용(판정에는 쓰면 안 됨, 노이즈 22배).
- **재시도별 기여** — 시도 1이 0.7, 시도 2가 0.95면 재시도가 실제로 일했다는 증거.

## 4. 판정 시점 문제

### 4.1 왜 매 프레임 못 재는가

top 카메라 시점에서 지우는 동안 **로봇 팔이 도형을 가린다.** 에피소드의 51%가 가려진 구간이다.

손목 카메라 대체는 실패했다 (`wrist_ink_probe.py`, 검증 A). 3가지 방식 전부 무신호:

| 방식 | 초반 대비 후반 대비비 | 판정 |
|---|---|---|
| 전체 프레임 dark+저채도 | 0.069 / 0.062 | 신호 없음 |
| 상단 40% crop | 0.0318 / 0.0314 | 신호 없음 |
| 시간축 정적 마스크로 그리퍼 제거 | 0.75~0.81x (역방향) | 신호 없음 |

원인은 각도가 아니라 **시점 변화**다. 손목 영상의 어두운 픽셀 분산을 잉크가 아니라
카메라 움직임·그리퍼·케이블이 지배한다. top은 target/distractor 분리가 20배인데
wrist는 최대 1.8배.

`ink_metric.dense_progress()`(가려진 픽셀만 제외하고 밀도 측정)는 관측 가능 프레임을
0%→58%로 늘렸지만, 판정에 쓰면 distractor 노이즈가 0.009→0.195로 폭증한다.
**진행도 곡선 전용, 판정 불가.**

### 4.2 채택: 시도 경계 판정

정책은 한 시도가 끝나면 팔을 빼고, 그 순간 보드가 드러난다.
**판정을 chunk 경계가 아니라 시도(attempt) 경계에서 한다.**

```
set_reference(park 프레임)          # 시도 전
  → 정책 실행 (max_steps)
  → park 강제
  → check(park 프레임)              # 시도 후
  → 실패면 재시도
```

부수 효과로 async client의 chunk 큐 문제가 사라진다.
`9__run_client.sh`는 `ACTIONS_PER_CHUNK=50, FPS=30` = 1.67초치 동작을 미리 큐에
쌓고 80% 소비 시점에 다음 chunk를 요청한다. chunk 중간에 끼어들려면 큐를 비워야 하고
그러면 async의 이점이 사라진다. 시도 경계 판정은 이 문제를 우회한다.

### 4.3 park 없이 판정할 수 있나 — 검토한 대안

| 대안 | 평가 |
|---|---|
| 손목 캠 | **불가.** 검증 A에서 실패 (§4.1) |
| 고정 사이드 웹캠 추가 | **유망하지만 지금은 불필요.** §4.4 |
| 팔을 도형 bbox 밖으로만 최소 이동 | park보다 이득이 작다. 어차피 정지·정착 시간이 필요하고, "bbox 밖" 판정에 기구학 계산이 붙는다 |
| 가려진 픽셀 제외 밀도(`dense_progress`) | **판정 불가** (노이즈 22배 증가) |
| 팔 세그멘테이션 후 인페인팅 | 가려진 곳의 잉크를 지어내는 것 — 판정 근거가 될 수 없다 |

**park의 실제 비용은 크지 않다**: 정책은 데모대로 어차피 시도 끝에 팔을 뺀다.
러너가 강제하는 것은 보험이다. 추가 비용은 정착 대기 약 1초 × 재시도 횟수.

### 4.2.1 "로봇이 스스로 비켜준다" — 검증됨. 그러나 게이트를 대체하지 못한다

실물에서 정책이 지우다가 팔을 살짝 빼고 다시 붙는 것처럼 보인다는 관찰이 있었다.
이게 사실이면 그 창에서 판정할 수 있고, 시도 중간 조기 종료와 park 폐지가 가능해진다.
`retreat_analysis.py`로 시연 29개(0802)를 재서 확인했다.

| 항목 | 값 |
|---|---|
| 물러남(노출 창)이 존재하는 에피소드 | **29/29 (100%)** |
| 창 길이 중앙값 | 138 프레임 (4.6초) |
| 노출 창 총 개수 | 43 |
| 그중 **부분 지워짐**(0.05 < erased < 0.9) | **4개 (9%)** |
| 첫 창에서 관측된 erased 중앙값 | **1.00** |

**관찰은 사실이지만 해석이 틀렸다.** 물러남은 실재하고 100% 재현되지만,
그 순간의 `erased_frac`은 **0.00 아니면 1.00으로 갈린다.** 즉 팔이 비켜주는 때는
"아직 접촉 전"이거나 "이미 다 지운 뒤"이지, **지우는 도중에 확인차 비켜주는 게 아니다.**

따라서:

- 시도 **중간** 판정은 여전히 불가능하다 → §4.2의 시도 경계 판정이 옳다. 게이트는 필요하다.
- 게이트가 하는 일은 "언제 지웠는지 알아내는 것"이 아니라
  **"다 지웠는데도 계속 닦는 것을 멈추고(A), 덜 지웠으면 다시 시키는 것(B)"** 이다.
  물러남이 있다고 그 둘이 해결되지는 않는다.
- 오히려 이 결과가 **증상 B의 원인을 다시 확인해 준다** — 시연에 "부분적으로 지워진
  보드를 물러나서 바라보는" 상태가 사실상 없다(4/43). 정책은 그 상태를 본 적이 없다.
  리커버리 데이터(§6.3, 로드맵 조합 3)가 필요한 이유가 여기 있다.

> 방법론 함정 하나. "노출 창이 완료 시점보다 이른가"로 재면 안 된다. 완료 시점은
> envelope으로 찾는데 envelope은 **가려지지 않은 프레임에서만** 갱신되므로, 완료가
> 처음 관측되는 프레임은 정의상 노출 창 안이다. 실제로 그 비율은 0.98이 나왔고
> 아무 정보가 없다. 창마다 `erased_frac`을 직접 재야 한다.

산출물: `outputs/analysis/retreat/demo_0802.{png,csv,json}`

### 4.4 사이드 카메라를 추가한다면

**증상 A(조기 종료)에는 필요 없다.** 필요해지는 경우는 dense progress나 보상 신호가
필요할 때다. 손목 캠이 실패한 원인은 시점이 계속 움직여서였고, **고정 카메라는 그
실패 원인이 없다.** 낮고 비스듬한 각도면 위에서 내려오는 팔에 덜 가린다.

설계상 중요한 점: **이 카메라는 정책 관측에 넣지 않는다.** 판정기 전용 센서로 따로
읽으면 데이터셋 feature도 체크포인트도 안 건드린다.

**휴대폰은 비권장.** `ink_metric`은 흰 보드 대비 어두운 픽셀 비율로 잉크를 재는데,
휴대폰의 자동 노출·화이트밸런스가 이 임계를 흔든다. 팔이 화면에 들어오면 노출이
크게 바뀐다. 마운트 흔들림, 스트리밍 지연도 있다.
→ **노출 수동 고정이 되는 USB 웹캠** 또는 RealSense 추가가 맞다.

도입 시 검증: 그 각도 영상에 `ink_metric`을 돌려 target/distractor 분리도를 잰다.
비교 기준이 이미 있다 — top 110배, wrist 1.8배.

### 4.5 판정 과정의 병목 — 확인해야 할 것

**★ 노출 드리프트 (가장 위험, 코드 확인 완료)**
`EraseChecker.set_reference()`는 기준 프레임에서 `ink_thr = white * dark_ratio`를
한 번 계산하고, `check()`는 그 값을 그대로 재사용한다
([erase_check.py](../scripts/tools/erase_check.py)의 `ref["ink_thr"]`).
녹화 데이터에서는 같은 영상 안이라 문제가 없었지만, **추론 중에는 시도 전과 후 사이에
수십 초가 흐르고 그 사이 RealSense 자동 노출이 움직일 수 있다.**
노출이 밝아지면 잉크가 덜 검게 잡혀 `erased_frac`이 부풀고, 어두워지면 반대다.
→ 검증 항목: 시도 전/후 프레임의 보드 흰 영역 밝기를 비교. 차이가 크면
   (a) RealSense 노출·화이트밸런스 수동 고정, 또는 (b) 매 프레임 white를 재추정.

**시간 비용**
시도당 park 이동 + 정착 1초 + 캡처. 3회 재시도면 3배.
24초 에피소드 기준 5% 내외로 예상되지만 park 이동 시간은 실측 필요.

**상태 비가역성**
지운 마카는 되돌릴 수 없다. 재시도는 항상 이전 시도 위에 쌓인다.
`set_reference`는 **시도 1 이전에 한 번만** 잡으므로 `erased_frac`은 누적값이다
(이게 맞는 설계다). 단, 재시도 간 개별 기여를 보려면 별도 기록이 필요하다.

**도형 미검출**
`set_reference`가 도형을 못 찾으면 `RuntimeError`. 오프라인에서 119/120이었지만
조명이 다른 환경에서는 다시 확인해야 한다.

**park 자세에서의 가림·그림자**
park 자세가 보드를 가리거나 도형에 그림자를 드리우면 판정이 통째로 무의미해진다.
`follower.parking()`이 실제로 어떤 자세인지 **눈으로 확인해야 한다.**

## 4.6 "어떤 도형을 지우던 중인지"를 어떻게 아는가

계획 1의 "덜 지운 곳에 추가 지시"를 하려면 세 가지를 알아야 한다.
**셋 다 VLA에서 값을 꺼낼 필요가 없다.** 어디서 오는지 갈라보면:

| 알아야 할 것 | 출처 | 상태 |
|---|---|---|
| ① 어떤 **종류**를 지워야 하는가 | **우리가 준 task 문자열** | 이미 있음 |
| ② 그중 어떤 **개체**인가 | 판정기 (`set_reference` 스냅샷) | 이미 있음 |
| ③ 그 개체의 **어디가** 남았는가 | 판정기 확장 필요 | 미구현 |

### ① 종류 — VLA에게 물을 필요가 없다

`--task "erase the triangle"` 과 `--target triangle`은 **우리가 정해서 넣는 입력**이다.
정책이 스스로 고르는 게 아니다. 그러니 "무엇을 지우려 했는가"는 처음부터 알고 있다.

VLA에서 이걸 읽어내려는 시도(어텐션 맵 등)는 하지 않는 게 맞다 — SmolVLA에 확립된
readout이 없고, 안다고 해도 그건 "정책이 무엇에 주목했나"이지 "무엇을 지워야 하나"가
아니다. **정답은 우리가 쥐고 있고, 정책이 그걸 따랐는지를 검사하는 쪽이 맞다.**

### ② 개체 — 판정기가 이미 기억하고 있다

`set_reference()`가 시도 전 프레임에서 도형을 전부 검출해 `label#i` 키로 bbox와
초기 잉크량을 저장한다. 같은 종류가 여러 개면 `min`으로 집계하므로 "하나만 지운"
경우를 실패로 잡는다(§2.5).

즉 개체 식별은 **판정기 안에 이미 있다.** 도형이 매번 새로 그려져도, 매 시도 전에
스냅샷을 다시 뜨므로 문제없다.

### ③ 위치 — 판정기 확장으로 얻는다 (미구현)

bbox 안에서 잔여 잉크 마스크(`gray < ink_thr`)의 **중심과 면적**을 내면 된다.
`ink_metric`에 몇 줄이다. 출력 예: `triangle#0: erased 0.62, 잔여 중심 (좌하단), 잔여 면적 38%`.

**남은 문제는 이걸 정책에 어떻게 전달하느냐다.** 후보:

| 방법 | 평가 |
|---|---|
| 언어 프롬프트 변경 (`"erase the bottom-left part of the triangle"`) | 학습 데이터에 그런 문장이 없다 → 분포 밖. 방향 어휘를 포함한 데이터를 새로 모아야 함 |
| 좌표 조건화 (관측에 목표 좌표 추가) | 모델 입력 구조 변경 → 재학습 필수 |
| 그냥 같은 task로 재시도 | **지금 구조.** 정책이 부분 지워진 상태를 본 적이 없어 증상 B가 그대로 남음 |

→ 결국 ③은 **리커버리 데이터 없이는 해결되지 않는다.** 위치를 알아내는 것 자체는
쉽지만, 그 정보를 쓸 통로가 없다. 위치 정보의 당면 용도는 **정책 전달이 아니라
진단과 데이터 라벨링**이다(어느 부위가 자주 남는가 → 리커버리 데이터를 어디에 모을까).

### 보너스: 가림을 신호로 쓰기 — 정책이 실제로 뭘 지우고 있었나

가림이 판정을 막는 방해물이지만, **"어느 도형을 작업 중인가"에는 오히려 신호다.**
팔은 자기가 지우는 도형을 가린다.

```
매 프레임: 각 도형 bbox에서 "잉크도 배경도 아닌" 픽셀(=팔/그리퍼) 비율을 잰다
        → 시도 내내 가장 오래 가려진 bbox = 정책이 붙어 있던 도형
```

이게 왜 쓸모 있냐면 — **잉크를 못 봐도, 정책이 엉뚱한 도형에 붙어 있었는지를
접촉 구간 내내 알 수 있다.** `max_distractor_erased`는 "결과적으로 지웠는가"만 보는데,
이건 "의도가 어디로 갔는가"를 본다. grounding 실패를 잉크가 지워지기 전에 잡는다.

미구현이고 실제 프레임으로 튜닝이 필요하다(팔 픽셀을 어떻게 정의할지 —
채도·명도 조합, 또는 시간축 변화량). 우선순위는 ③보다 낮다.

## 5. HIL 개입

### 5.1 키보드 토글 채택

처음에는 리더암 움직임으로 개입을 자동 감지하려 했다. 실패했고, 그 과정에서
mock 테스트가 버그 두 개를 잡았다:

1. **이탈 판정에 편차를 쓰면 안 된다.** 개입이 시작되면 팔로워가 리더를 따라가므로
   편차가 0으로 수렴 → 사람이 잡고 있는데 즉시 반환.
2. **진입 판정에 편차만 쓰면 안 된다.** 손을 뗀 뒤 리더가 그 자리에 남으면 정책이
   팔로워를 몰고 가면서 편차가 다시 커짐 → 무한 재개입.

고칠 수는 있지만 임계값 3개(`takeover_th`, `still_speed`, `still_steps`)를 실측으로
맞춰야 하고 중력 처짐에 따라 재조정이 필요하다.
**명시적 키보드 토글은 이 전부를 없앤다.** 오검출이 원리적으로 0이다.

LeRobot HIL-SERL도 같은 선택을 한다 — `space`로 정책에서 인계, 다시 `space`로 반환.
`pynput`은 이미 리포에서 쓰고 있다(`teleop_ui.py`).

현재 매핑: **`space` = 개입 on/off, `q` = 시도 중단.**

> 양손이 리더암에 있으면 키를 못 누른다. 거슬리면 USB 풋페달이 표준 해법이다.

### 5.2 ★ PiPER 고유 제약 — 리더암은 명령을 받을 수 없다

리포 소스에서 확인한 사실 ([piper_leader.py](../lerobot_robot_piper/piper_leader.py) `connect()` 주석):

> Piper 공식 dual-arm 문서: "Master arm: only sends control frame messages."
> 즉 leader(master) 팔은 EnableArm 대상이 아님 — 사람이 손으로 움직이는 값을 CAN으로
> 흘려보내기만 하고, 모터 서보 활성화가 필요 없음(**활성화 시도 시 계속 타임아웃남,
> 실제 하드웨어에서 확인됨**).

이게 왜 중요하냐면 — LeRobot HIL-SERL 문서는 SO101 리더를 권장하면서
**"reduced gears가 있어 정책 실행 중 리더가 팔로워를 추종할 수 있고, 그래서 인계가
부드럽다"** 고 명시한다. PiPER는 이게 **불가능하다.** 리더를 구동할 수 없으니까.

따라서 개입 시점에 리더와 팔로워는 **반드시 어긋나 있다.** 24초간 정책이 팔로워를
몰고 다녔으니 어긋남이 클 수도 있다.

### 5.3 해법: 델타(클러치) 인계 — park 정렬 불필요

세 가지 선택지를 검토했다.

| 방식 | 평가 |
|---|---|
| park 갔다가 리더 각도 맞추고 재개 | 동작은 한다. 그러나 **개입의 목적을 무너뜨린다** — 실패가 벌어지는 순간에 끼어들어야 하는데, park를 거치면 그 순간이 지나간다. 매 개입마다 수 초 + 사람이 정렬해야 함 |
| 리더 절대 자세를 그대로 전송 | 팔로워가 튄다. `MAX_RELATIVE_TARGET=5.0` 클램프가 물리적으로는 막지만, 그만큼 스텝당 5씩 미지의 경로로 기어간다 |
| **리더 변화량만 전송 (클러치/인덱싱)** | **채택.** 점프가 원리적으로 0 |

```
engage 시점:  lead0 = 리더 자세,  foll0 = 팔로워 자세
개입 중:      target = foll0 + gain × (leader_now − lead0)
```

인계 첫 스텝의 target이 팔로워 현재 자세와 정확히 같으므로 **어긋남이 아무리 커도
점프가 없다.** 마우스를 들었다 놓는 것(인덱싱), 자동차 클러치와 같은 원리다.
테스트 `test_clutch_no_jump_on_engage`가 60만큼 어긋난 상태에서 이를 검증한다.

트레이드오프:
- 리더의 절대 자세가 팔로워의 절대 자세와 더 이상 대응하지 않는다.
  짧은 교정 개입에는 문제없지만, 긴 개입에서는 사람의 감각과 어긋날 수 있다.
- `gain < 1`로 두면 정밀 보정이 쉬워진다(`--clutch-gain`).
- 개입을 껐다 켜면 기준점이 다시 잡힌다(`test_clutch_reengage_uses_new_reference`).

### 5.3.1 그래도 리더암을 팔로워와 비슷한 자세로 두는 게 좋다 — 안전이 아니라 조작감 때문

**필수는 아니다.** 클러치 방식이라 어긋남이 아무리 커도 점프는 0이다.
그래도 space를 누르기 전에 리더를 팔로워와 대충 맞춰두면 세 가지가 좋아진다.

1. **직관적 대응.** 관절 공간 델타라서 관절별 각도 변화는 정확히 1:1로 전달되지만,
   **같은 관절 변화가 만드는 손끝 움직임은 자세에 따라 다르다.** 리더가 팔로워와
   비슷한 형상이어야 "앞으로 민다"가 팔로워에서도 앞으로 나간다.
2. **가동 여유(headroom).** 리더 관절이 자기 한계 근처에 있으면 그 방향으로 더 못 민다.
   반대로 팔로워가 한계 근처면 리더를 밀어도 클램프에 걸린다.
   대충 맞춰두면 양쪽 다 여유가 최대가 된다.
3. **누적 오차.** 개입이 길어질수록 델타가 쌓인다. 시작이 비슷하면 어긋남이 덜 커진다.

**실전 절차**: 정책이 도는 걸 보다가 개입이 필요해지면 →
리더암을 눈대중으로 팔로워 자세에 맞춘 뒤 → `space` → 조작 → `space`로 반환.
맞추는 동안 팔로워는 정책이 계속 몰고 있으므로 완벽할 수 없다. 대충이면 된다.

> 로그의 `engage_deviation`이 인계 시점의 실제 어긋남을 기록한다.
> 이 값이 매번 크면 "개입이 필요할 것 같을 때 미리 리더를 근처에 두는" 습관이 필요하다는 뜻이다.

`deviation()`은 판정에서 빠졌지만 **인계 시점 값을 로그에 남긴다**(`engage_deviation`).
나중에 자동 감지를 다시 시도할 때 실측 근거가 된다.

### 5.4 LeRobot HIL-SERL — 재사용 가능한 것과 아닌 것

LeRobot에 HIL-SERL이 이미 포팅되어 있다(`lerobot.rl.gym_manipulator`, PR #644).
**직접 재사용은 어렵지만, 왜 어려운지가 우리 설계 근거가 된다.**

| 항목 | HIL-SERL | 우리 | 재사용? |
|---|---|---|---|
| 개입 토글 | `space` | `space` | 설계 차용 ✓ |
| 개입 장치 | gamepad / keyboard / **leader** (`control_mode: "leader"`) | PiperLeader | 개념 동일 |
| 액션 공간 | **EE delta (x,y,z)**, URDF+IK 필수 | joint-space 정규화 | ✗ |
| 제어 주기 | 10 fps | 30 fps | ✗ |
| 권장 horizon | **5~10초** | 24초 | ✗ |
| 판정기 | resnet10 학습 분류기, 이진, threshold 0.5 | 룰베이스 픽셀 metric | 우리가 더 정확 |
| 종료 | `terminate_on_success: true` | 우리 게이트 | 개념 동일 ✓ |
| 학습 | SAC actor-learner (gRPC 2프로세스) | SmolVLA flow matching | ✗ |
| 이미지 | crop ROI → 128×128 | 640×480 | 조정 필요 |

특히 문서가 명시하는 대목: *"learning in joint space for reinforcement learning in
manipulation is often a harder problem — some tasks are nearly impossible to learn in
joint space but become learnable when the action space is transformed to end-effector
coordinates."* 우리는 joint-space이고 URDF/IK 경로가 정비되어 있지 않다.

**결론: HIL-SERL 파이프라인에 올라타지 않고, 자체 러너(`erase_run.py`)로 간다.**
차용하는 것은 (a) space 토글, (b) `terminate_on_success` 개념,
(c) intervention rate를 학습 진척 지표로 보고하는 관행.

### 5.5 추론 3방식(`--aggregate-fn`)이 게이트·HIL과 어떻게 얽히는가

`--aggregate-fn`은 정책이 뱉은 chunk들을 **겹치는 구간에서 어떻게 합칠지**를 정한다.
구현은 `action_smoothing.py`.

| 값 | 수식 | 출처 |
|---|---|---|
| `weighted_average` (기본) | `0.3·old + 0.7·new`, 새 chunk가 올 때마다 pairwise 적용 | lerobot async_inference |
| `latest_only` | `new` — 최신 chunk가 이전 것을 그냥 덮는다 | lerobot async_inference |
| `temporal_ensemble` | 겹치는 예측 **전부**를 `exp(-m·i)`로 한 번에 평균 (m=0.01 ≈ 균등) | ACT |

#### 판정·잔량 추정에는 영향이 없다 (구조적으로)

판정은 **시도 경계의 park 프레임 한 장**에서 카메라로 잰다(§4.2). 액션 파이프라인을
전혀 지나지 않으므로 `aggregate_fn`과 경로가 겹치지 않는다. `residual()`도 같은
프레임을 쓴다.

단, **간접 경로는 있다** — 방식이 궤적의 부드러움을 바꾸고, 그게 지우개가 보드에
제대로 닿는지를 바꾸고, 그래서 `erased_frac`의 **값**이 달라진다. 측정 방법이 아니라
측정 대상이 달라지는 것이다.

> ⚠️ 평가할 때의 함의: 게이트 on/off를 비교하는 표(§8)에서는 `aggregate_fn`을
> **반드시 고정**해야 한다. 안 그러면 게이트의 효과와 스무딩 방식의 효과가 섞인다.

#### HIL에는 영향이 있다 — 개입이 아니라 **반환** 시점에

인계(engage)는 방식과 무관하게 안전하다. 클러치가 `foll0 + gain·(leader − lead0)`로
첫 스텝 목표를 팔로워 현재 자세와 같게 만들기 때문이고, 60만큼 어긋난 상태에서
`test_clutch_no_jump_on_engage`가 이를 검증한다(§5.3).

문제는 반환이다. 개입 중 러너는 **매 스텝 `pipeline.reset(action)`** 을 호출한다
(`piper_infer_runner.py`, "개입 중 스무딩 파이프라인은 계속 정책 궤적을 밀고 있으므로"
주석). 이건 옳은 처리다 — 안 하면 반환 첫 스텝에 목표가 튄다. 그런데 `reset()`은
**앙상블 버퍼를 통째로 비우므로**, 반환 직후에는:

1. `pending_steps == 0` → 루프가 `_await_chunk()`로 **추론 1회(약 115ms ≈ 3~4스텝)를
   기다린다.** 개입을 껐다 켤 때마다 이 정지가 생긴다.
2. 새 chunk가 하나뿐이라 `votes == 1` → **겹침 평균이 없다.** 즉 `docs/policy/smoothing.md`가
   확립한 스무딩이 하필 **가장 튀기 쉬운 순간에 빠진다.**

여기서 방식별로 갈린다:

| 방식 | 반환 직후 잃는 것 | 회복 |
|---|---|---|
| `temporal_ensemble` | 가장 크다. 평상시 여러 표를 균등 평균(m=0.01)하다가 1표로 떨어진다 | chunk가 몇 번 겹쳐 쌓일 때까지 |
| `weighted_average` | 중간. pairwise라 표 수에 덜 민감하다 | 빠름 |
| `latest_only` | 없다. 원래 항상 최신 1개만 쓴다 | 즉시 |

**역설적인 결론**: HIL을 많이 쓰는 실험에서는 가장 부드러운 방식(`temporal_ensemble`)이
반환 시 가장 거칠어진다. 반대로 개입이 없는 순수 게이트 실험에서는 이 항이 0이라
아무 차이가 없다.

**아직 실물로 확인 안 했다.** 확인에 필요한 데이터는 `erase_run_log.steps.npz`의
`attempt{i}_votes`와 `attempt{i}_intervention`이다(둘 다 저장하도록 해 뒀다).
반환 프레임을 기준으로 votes가 1에서 회복되는 데 걸린 스텝 수를 방식별로 세면 된다.
어제 실측(940스텝, 개입 0회)에서는 `rate_clamp`가 한 번도 안 걸렸고 명령-실측 편차가
평균 0.84라, 개입이 없는 한 이 항은 문제가 아니라는 것까지는 확인됐다.

## 6. 개입 데이터로 학습 (계획 4) — 전제 조건

아직 구현하지 않았다. 착수 전에 알아야 할 것들.

### 6.1 DAgger 계열의 핵심 문제

- **covariate shift**: BC로 학습한 정책은 자기 실수가 만든 상태를 본 적이 없다.
  DAgger는 학습자의 정책으로 굴러간 상태에서 전문가 라벨을 모아 이를 메운다.
  우리 증상 B가 정확히 이 문제다.
- **HG-DAgger (human-gated)**: 사람이 게이트 역할을 하고 개입 구간만 데이터로 쓴다.
  우리 설계와 같다. 한계로 지적되는 것은 **1:1 상시 감독이 필요해 확장성이 없다**는 점.
- **ConRFT가 HG-DAgger를 깐 이유**(p.6): 사람 교정이 일관성 없고 노이즈가 많아
  정밀 접촉 과제(Insert Wheel, Hang Chinese Knot)에서 개선이 제한적이었다.
  Table I에서 HG-DAgger는 에피소드 길이를 1.1×밖에 못 줄였다(HIL-ConRFT는 1.9×).
  → **리더암은 게임패드보다 노이즈가 작다**는 게 우리 반론 근거다.

### 6.2 우리 경우의 추가 제약

- **자동 리셋 불가.** 지운 마카를 되돌릴 수 없다. ConRFT는 스크립트 모션이나 사람 손으로
  리셋했고, RL-100은 이를 미해결 한계로 명시했다("learned or semiautomated reset
  strategies"). 우리는 매 에피소드 사람이 다시 그린다.
- **credit assignment.** 30fps × 720스텝이면 에피소드당 결정이 720개다.
  HIL-SERL이 다루는 10fps × 5~10초(50~100스텝)보다 한 자릿수 크다.
  sparse reward만으로 RL을 돌리기에는 불리하다.
- **데이터 형식.** 개입 궤적을 LeRobotDataset으로 저장하려면 `add_frame`/`save_episode`
  경로를 타야 하고, `intervention` 플래그를 어느 필드에 넣을지 정해야 한다.
  현재 `erase_run.py`는 JSON 로그만 남긴다 — 데이터셋 변환은 별도 작업.

### 6.3 가장 게으른 경로 (권장)

RL로 가기 전에 **BC 재학습부터** 시도한다:
개입 궤적 + `erase_check`의 성공 라벨 → 기존 데이터셋에 추가 → SmolVLA fine-tune.
이게 iRe-VLA / RLDG가 보고한 "RL로 모은 데이터를 SFT에 쓴다" 구조이고,
ConRFT Table III에서 RLDG가 SFT 대비 크게 앞선 결과가 있다(83.3 vs 58.3).
파이프라인이 이미 있으니 추가 인프라가 거의 없다.

## 8. 보고할 지표

ConRFT Table I 형식을 따른다 — **성공률과 에피소드 길이를 나란히.**

| 조건 | 성공률 (%) | 평균 스텝 | 평균 시도 | 개입률 (%) |
|---|---|---|---|---|
| 게이트 없음 (baseline) | | 고정 = max_steps | 1 | — |
| 게이트만 | | | | 0 |
| 게이트 + HIL | | | | |

비교 기준:
- ConRFT: 에피소드 길이 1.9× 단축 (HG-DAgger는 1.1×)
- RL-100: 실패 포함 822 → 322 스텝 (60.8% 감소)

우리만 낼 수 있는 것:
- **판정기 정확도** — 119/119, target 0.987 vs distractor 0.009, 분리 110배
- **잔여량 분포** — 이진 판정만 하는 선행연구가 못 내는 표
- **distractor erased_frac = language grounding 실패율**
- **intervention rate 곡선** — HIL-SERL / ConRFT Fig. 3과 같은 축

### 8.1 통계 프로토콜 — 표를 어떻게 채울 것인가

지금까지는 "무엇을 잴까"였고, 여기부터는 **"몇 번 재고 어떻게 보고할까"** 다.
로봇 조작 논문이 가장 자주 지적받는 대목이고(n이 작은데 점추정만 보고),
`erase_stats.py`가 아래를 자동으로 계산한다.

#### 조건당 n

선행연구 관행: ConRFT는 조건당 20 trial, HIL-SERL은 20~100, RL-100은 task당 수백.
우리는 **에피소드마다 사람이 도형을 다시 그려야 해서 자동 리셋이 불가능**하다(§6.2).
현실적 상한은 세션당 30~40회다.

→ **조건당 n = 20**을 기준으로 잡는다. 조건 3개(baseline / 게이트 / 게이트+HIL)면
60회, 도형 3종을 균형 배치하면 조건·도형당 6~7회. 세션은 나눠도 되지만
**조명이 판정 임계에 영향을 주므로 세션 ID를 반드시 기록**한다(§4.5 노출 드리프트).

#### 성공률에는 점추정 대신 구간을 붙인다

n=20에서 "성공률 65%"는 사실상 아무 말도 아니다. 95% 신뢰구간이 ±20%p 넘는다.
**Wilson score 구간**을 쓴다 — 정규근사(Wald)는 n이 작거나 p가 0/1에 가까울 때
구간이 음수로 새거나 폭이 0이 되는 알려진 문제가 있고, Wilson은 그 두 경우 모두
정상 동작한다. 20/20이 나와도 구간이 [83.9%, 100%]로 나오지 [100%, 100%]가 아니다.

#### 조건 간 비교

| 비교 대상 | 검정 |
|---|---|
| 성공률 (이진, 조건 간 독립) | **Fisher exact test** — n이 작아 카이제곱의 근사 조건을 못 맞춘다 |
| 에피소드 길이·스텝 수 (연속, 분포 비대칭) | **Mann–Whitney U** + **bootstrap 신뢰구간**. 정규성을 가정하지 않는다 |
| `erased_frac` 분포 | 분포 자체를 그림으로 낸다(ECDF). 평균만 내면 이중분포가 지워진다 |

효과 크기도 같이 낸다 — 성공률 차이는 절대 %p와 **Cohen's h**, 길이는
**Cliff's delta**(비모수). p값만 보고하는 표는 리뷰에서 지적받는다.

#### 사전 등록해야 할 것 (돌리기 전에 고정)

임계값을 결과 보고 고르면 그건 튜닝이지 평가가 아니다. 아래를 **실험 전에** 못 박는다.

- 성공 임계 `target_erased ≥ 0.9`, `max_distractor ≤ 0.10`
- 시도 상한 `max_steps = 940`, 재시도 상한 3
- `aggregate_fn`은 조건 전체에서 **고정**(§5.5) — 안 그러면 교란된다

민감도 분석은 사후에 해도 되지만 **부록으로**, 주 결과는 사전 등록값으로 낸다.
`erase_stats.py --sensitivity`가 임계값을 훑으며 결론이 뒤집히는 지점을 찾아준다
(§2.5의 "0.15 → 0.10 민감도 분석" 항목이 이걸로 닫힌다).

#### 판정기 자체의 신뢰도 — 치과 planimetry 관행을 그대로 가져온다

우리 판정기는 **자동**이라 사람 판정과 달리 재현성이 100%다(같은 입력 → 같은 출력).
그래서 재야 하는 건 rater 간 일치가 아니라 **사람 눈과의 일치**다.

- 무작위 40장(성공/실패 균형)을 사람이 라벨링 → **Cohen's kappa**
- 연속값은 사람이 매긴 "몇 % 지워졌나"와 **Bland–Altman**(bias + limits of agreement)
- plaque planimetry가 ICC 0.930을 보고하는 것과 같은 자리에 우리 값을 넣는다

이건 §3의 "전체 영상 대비 119/119 일치"와 다른 축이다. 그건 우리 metric 두 버전 간
일치이고, 이건 metric과 사람 사이의 일치다. **둘 다 있어야 한다.**
