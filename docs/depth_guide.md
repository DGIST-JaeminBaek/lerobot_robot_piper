## 1. 현재 구현 (jmbaek, `13c8b06`)

상세는 **`docs/depth/README.md`(583줄)**가 1차 출처다. 여기서는 판단에 필요한 만큼만 정리한다.

### 왜 백포트인가

LeRobot 0.6.0에 공식 depth 양자화·인코딩이 들어갔지만 **0.5.0 이상은 Python 3.12를
요구**한다. 이 프로젝트는 ROS2 Humble의 `rclpy` 때문에 **Python 3.10**에 묶여 있어,
공식 구현을 0.4.4의 저장 구조(PNG → 에피소드 종료 후 일괄 인코딩)에 맞춰 이식했다.

### 파이프라인

```
RealSense z16 depth (uint16, mm)
  → 12-bit 로그 양자화 (code 0–4095)
  → 임시 16-bit PNG (PIL I;16)
  → HEVC + gray12le + x265 lossless (.mp4)
  → PyAV 디코딩 → 역양자화 → float32 mm
```

| 파라미터 | 값 |
|---|---|
| 양자화 | 12-bit **로그** |
| 범위 | 0 – 10 m |
| log shift | 3.5 m |
| codec / pix_fmt | HEVC / `gray12le` |
| 옵션 | `x265-params=lossless=1` |

**"무손실"의 정확한 의미**: 12-bit code가 인코딩 전후 동일하다는 뜻. 16→12bit 양자화
자체에는 오차가 있고, 합성 10 mm–10 m 데이터에서 **최대 2 mm**로 측정됐다.

### 메타데이터

`features[*].info`에 `is_depth_map`, `video.codec`, `video.pix_fmt`,
`video.depth_min/max`, `video.shift`, `video.use_log`가 저장된다.
**읽을 때 이 값들이 녹화 시점과 같아야 한다.** `DepthFeature`가 shape `(H, W, 1)`과
이 메타데이터를 함께 전달한다.

`depth_min`을 공식 기본값 0.01 m가 아니라 **0.0 m**로 바꾼 것이 세심한 부분이다 —
RealSense가 invalid 픽셀을 0 mm로 돌려주는 의미를 보존하기 위함이고, 로그 전에
3.5 m를 더하므로 `0 mm → code 0 → 0 mm`로 왕복한다.

### 검증 결과 (실물)

D435IF 2대, 1280×720, 30 fps, 5초:

| 항목 | 결과 |
|---|---|
| TOP / WRIST depth | **150/150 프레임 전 픽셀 code 일치** |
| dataset reload | 성공 |
| TOP 유효 depth 비율 | 87.67 % |
| WRIST 유효 depth 비율 | 64.62 % |

## 2. 왜 이 방식이 우리 것보다 나은가

### 문제의 뿌리 — 동영상 코덱은 컬러용이다

LeRobot은 카메라 데이터를 동영상으로 저장하는데, 코덱은 **3채널 8비트 컬러**를 가정한다.
depth는 **1채널 16비트**라 모양이 안 맞는다. 여기서 두 갈래가 나온다.

| | 우리 (폐기) | jmbaek (채택) |
|---|---|---|
| 발상 | depth를 **색으로 칠해** 컬러 사진으로 위장 | 파이프라인이 **12비트 흑백**을 저장하도록 개조 |
| 구현 비용 | 코드 몇 줄 | LeRobot 내부 6개 파일 수정 |
| 표현 단계 | 256 | **4096** |
| 압축 | 손실 (`yuv420p`, `crf30`) | **무손실** |

### 정규화 창 — 우리 방식의 치명적 약점

256단계뿐이라 **"어느 거리 구간에 예산을 쓸지" 미리 정해야 했다:**

```
DEPTH_MIN_M=0.20 / DEPTH_MAX_M=0.80    # 이 밖은 전부 양 끝에 뭉갬
```

여기서 두 가지 사고가 예정돼 있었다.

1. **창을 잘못 잡으면 백지** — 우리 설정은 0.2–0.8 m인데 보드는 약 1 m다. 전부 창 밖이라
   단색 이미지가 나온다. (창을 옮기면 해결은 가능)
2. **wrist 캠은 구조적으로 불가** — 창은 상수인데 wrist 캠은 거리가 계속 변한다.
   팔을 내리면 전부 최소값에, 올리면 최대값에 포화돼 **같은 표면이 팔 자세에 따라
   다른 색으로 찍힌다.** 값 조정으로 해결되는 문제가 아니다.

**jmbaek 방식에는 창이 없다.** 0~10 m를 항상 담으므로 두 문제가 통째로 사라진다.

### 로그 양자화

"0~10 m를 4096칸이면 성기지 않나?" → **칸을 균등하게 안 나눈다.** 가까울수록 촘촘하다.
가까운 물체는 mm가 중요하지만 5 m 밖은 아니기 때문이다.

실제 코드(`depth_utils.py`의 `quantize_depth` — 자연로그, shift 3.5)로 계산한 값:

| 거리 | 1칸 | 최대 오차 |
|---:|---:|---:|
| 0.3 m | 1.25 mm | 0.63 mm |
| **1.0 m** (우리 보드) | **1.48 mm** | **0.74 mm** |
| 2.0 m | 1.81 mm | 0.91 mm |
| 10.0 m | 4.45 mm | 2.23 mm |

### 정면 비교 (1 m 지점)

| | 1칸 | 최종 실측 오차 |
|---|---:|---:|
| 우리, 창 0.25 m로 **완벽히** 맞췄을 때 | 0.98 mm | **중앙값 2.35 mm** |
| 우리, 창 0.6 m | 2.34 mm | 그보다 나쁨 |
| **jmbaek** | 1.48 mm | **0.74 mm** |

**이론상으로는** 창을 완벽히 맞추면 우리가 1.5배 촘촘하다.
**그런데 실제로는 3배 나쁘다** — 손실 압축 때문이다(§3).

## 3. 우리 실측 자료 — 폐기가 아니라 이사한다

컬러맵 방식의 손실을 측정한 값들이다. 저장 방식으로는 안 쓰지만 **§4의 dataloader
컬러맵 논의에 그대로 쓰인다.**

### 측정 방법

합성 depth(경사면 + 물체 + 1.5 mm 센서 노이즈 + invalid 홀) → turbo 컬러맵 →
lerobot 기본 설정(`libsvtav1`, `yuv420p`, `crf30`)으로 인코딩 → 디코딩 → 역컬러맵 →
원본 인덱스와 비교.

### 결과 (창 0.2–0.8 m, 2.35 mm/step 기준)

| | turbo | 회색조(대조군) |
|---|---:|---:|
| 중앙값 오차 | 2.35 mm | 2.35 mm |
| 95 % 오차 | 4.71 mm | 4.71 mm |
| 최대 오차 | **21.18 mm** | 9.41 mm |
| 10 mm 초과 픽셀 | 0.17 % | 0.00 % |

**손실의 주범은 비디오 압축이 아니라 8비트 양자화였다.** 중앙값이 정확히 양자화
1스텝(2.35 mm)과 같다. 다만 **turbo는 최댓값이 21 mm까지 튄다** — 무지개 컬러맵은
인접 depth가 전혀 다른 RGB로 매핑돼 크로마 서브샘플링이 큰 오차를 만든다.
회색조는 9.4 mm에서 멈춘다.

> ⚠️ 이 측정은 **정지 화면**이라 낙관적이다. 실제 녹화는 움직임이 있어 더 나쁠 수 있다.

### PNG 중간 파일 (관측된 부수 효과)

10초 스트림당 **RGB 20 MB vs depth(turbo) 79 MB — 4배.**
무지개 그라디언트는 PNG 압축이 잘 안 된다. jmbaek 방식(회색조 12비트)은 이 문제가 덜하다.

## 4. 우리가 기여할 수 있는 것 — 컬러맵을 학습 단계로

**SmolVLA의 비전 인코더(SigLIP)는 자연 RGB로 사전학습됐다.** 12비트 회색조 depth를
그대로 넣으면 분포 밖 입력이다. turbo 컬러맵은 자연 이미지에 가까운 색 통계를 만든다.

**그런데 이 둘은 충돌하지 않는다:**

```
저장:  jmbaek 방식으로 정확한 12-bit depth        (0.74 mm)
  ↓
학습:  dataloader에서 turbo 컬러맵을 씌워 SigLIP에 입력
```

양쪽 장점을 다 갖는다:

- 저장은 near-lossless
- **컬러맵·정규화 창을 재수집 없이 언제든 바꿀 수 있다** ← 우리 방식으로는 불가능했던 것
- "회색조 vs 컬러맵" ablation이 가능해진다
- §3의 측정치가 컬러맵 파라미터 선택의 근거가 된다

`docs/depth/README.md` §12를 보면 재생 뷰어들이 이미 컬러맵을 적용하고 있어 기계 장치는 있다.

> **미검증**: dataloader 컬러맵이 실제로 회색조보다 나은지는 실험해봐야 한다.
> Depth Helps(§5)의 결과를 보면 차이가 작을 가능성도 있다.

## 5. 관련 논문

### ⭐ Depth Helps: Improving Pre-trained RGB-based Policy with Depth Information Injection (IROS 2024)

[프로젝트](https://gewu-lab.github.io/DepthHelps-IROS2024/) · [arXiv](https://arxiv.org/html/2408.05107v1)

사전학습된 RGB 정책에 depth를 주입하는 방법을 다룬다. 우리 상황(SmolVLA 사전학습
모델에 depth를 얹기)과 가장 가깝다.

**중요한 수치**: RGB-D 입력 평균 성공률 **63.95 %** vs RGB-only **63.15 %** —
차이가 **0.8 %p**에 불과했다.

> **신중하게 읽어야 한다.** "depth가 무의미하다"가 아니라 "**해당 태스크·방법에서는**
> 이득이 작았다"는 뜻이다. 다만 **depth 비용(인코딩 2.1시간 + 학습 1.5배)에 비해
> 기대 이득이 크지 않을 수 있다**는 신호로 볼 근거는 된다.

### 배경 — 인코딩 방식 두 갈래

- **Turbo (Google, 2019)** — [블로그](https://research.google/blog/turbo-an-improved-rainbow-colormap-for-visualization/).
  jet의 false detail·banding을 고친 무지개 컬러맵. depth 시각화가 원래 용도.
  **지각적으로 균일하지 않다**(의도된 트레이드오프). 색맹 친화적이지 않다.
- **Pece, Kautz, Weyrich (2011), Adapting Standard Video Codecs for Depth Streaming** —
  [Eurographics](https://diglib.eg.org/handle/10.2312/EGVE.JVRC11.059-066).
  16-bit depth를 Y채널(거친 depth) + 크로마(위상 다른 삼각파)로 포장해 압축을 견디게 함.

**둘은 푸는 문제가 다르다.** Turbo는 "보이게", Pece는 "복원되게". jmbaek이 채택한
LeRobot 0.6.0 방식은 Pece 계열의 문제의식을 **전용 12비트 무손실 경로**로 더 간단히 푼다.

## 6. 비용 — 이제 여기가 유일한 제약

### 저장용량 — 문제 아님

1 TB 기준, 150 에피소드 × 30초:

| 시나리오 | 용량 | 1 TB 대비 |
|---|---|---|
| 현실 추정 | 2~10 GB | 0.2~1 % |
| 비관 (노이즈 많은 장면, 4스트림) | 68 GB | 6.8 % |

**최악을 잡아도 7 %다. 저장용량을 근거로 판단하지 말 것.**

### ⚠️ 인코딩 시간 — 진짜 제약

jmbaek 실측: **1280×720, 4스트림, 16코어 RTX 5090 워크스테이션 → 에피소드당 51.3초.**
150 에피소드면 **약 2.1시간이 순수 대기**다.

- **NVENC를 못 쓴다** — `gray12le` 단일채널 12비트를 지원하지 않아 **CPU x265 고정**
- 병렬화 개선도 기대만큼 안 나왔다(순차 54 s → 통합 병렬 51.3 s). 코어를 나누니 각
  인코딩이 느려져 상쇄됐고, x265/SVT-AV1의 스레드 스케일링 특성이라 손대기 어렵다

**완화책**
- **해상도 축소** — 640×480이면 픽셀 1/3, 대략 17초/에피소드 (추정, 미검증)
- **`video_encoding_batch_size`를 올림** — N개 모아서 인코딩. 총 시간은 같지만
  **언제 멈출지 고를 수 있다**(쉬는 시간·퇴근 전에 몰아서)

### ⚠️ 학습 시간 — 못 미룸

카메라 2대 → 3대면 SigLIP이 이미지를 **1.5배** 더 처리한다. 녹화 2.1시간은 일회성이지만
**학습 시간 증가는 실험을 돌릴 때마다 계속 붙는다.** ablation을 여러 번 돌릴 계획이면
이쪽이 더 큰 비용이다.

## 7. 판단

### 1차 수집(effort ablation용)에서는 빼는 것을 권장

**정확도나 구현 품질 때문이 아니다.** jmbaek 구현은 검증됐고 우리 것보다 명백히 낫다.
순수하게 **시간 대비 기대 이득** 문제다.

| 근거 | 상태 |
|---|---|
| ~~현재 창 설정이면 백지로 찍힘~~ | ❌ **소멸** (창 개념 자체가 없어짐) |
| ~~wrist 캠 구조적 불가~~ | ❌ **소멸** (가장 강했던 논거) |
| ~~CPU 성능 부족~~ | ❌ **철회** (녹화 PC가 5090 ×2 기계로 확인됨) |
| **ablation 표에서 depth는 6번, effort는 3~5번** | ✅ 유효 — **effort 실험은 depth 없이 돌아간다** |
| **인코딩 2.1시간 + 학습 1.5배** | ✅ 유효 |
| **Depth Helps의 이득이 0.8 %p** | ⚠️ 참고 — 기대 이득이 크지 않을 수 있다 |

**그리고 결정적으로 — depth는 모델 입장에서 "카메라 한 대 추가"와 완전히 동일하게
처리된다.** 나중에 붙여도 **코드 수정이 전혀 없다.** effort와 달리 서두를 이유가 없다.

### depth를 켜기로 한다면

- [ ] **해상도를 jmbaek 검증 설정(1280×720)과 맞출지 결정** — 팀 합의 필요.
      `docs/vla_fps_resolution.md` §4-1 참고 (SmolVLA는 어차피 512×512로 줄인다)
- [ ] `13c8b06` 병합 후 충돌 3곳 해결 (§8)
- [ ] 짧게 찍어 depth 영상이 실제로 쓸만한지 눈으로 확인
- [ ] `video_encoding_batch_size`로 인코딩 시점을 옮길지 결정
- [ ] 첫 에피소드 전에 확정하고 **수집 끝까지 바꾸지 말 것** (features 불일치 → 머지 불가)

## 8. 병합 완료 — 충돌 3곳 해결 내역

`13c8b06`을 우리 브랜치에 병합했다. 충돌 3곳은 아래와 같이 해결했다 — **depth는 전부 jmbaek 것을 그대로 채택**했고, 우리 쪽은 effort/안전 컷오프만 남겼다:

| # | 위치 | 우리 | jmbaek | 판단 |
|---|---|---|---|---|
| 1 | `_cameras_ft` | turbo 컬러맵 3채널 | `DepthFeature` 전용 타입 | ✅ **jmbaek 그대로 채택**, 우리 것 폐기 |
| 2 | `get_observation` | effort/vel 블록 | 카메라 병렬 읽기 재구성 (59 ms → 목표 33 ms) | ✅ 카메라는 jmbaek 그대로, effort 블록만 앞에 유지 |
| 3 | `send_action` | **effort 안전 컷오프** | `set_action` 타이밍 로깅 | ✅ 타이밍 로깅 유지 + **안전 컷오프 생존** |

**3번을 특히 주의해야 한다.** jmbaek 쪽 코드에는 안전 컷오프가 없다. 기계적으로
병합하면 **"팔이 뻗는" 사고를 막던 로직이 사라진다.** 의도적으로 뺀 것인지
브랜치가 갈려서 모르는 것인지 본인 확인이 필요하다.

### 함께 확인해야 할 것 — action 의미 변경

`13c8b06`은 depth 외에 **`lerobot_record.py`의 action 기록 방식도 고쳤다.**
원래 `send_action()`이 리턴하는 "실제로 로봇에 보낸 값"(offset 보정 완료)을 버리고
teleop raw 값을 저장하고 있었다. 이제 보정된 값이 저장된다.

> **이 수정 이전에 녹화된 데이터셋과 의미가 다르니 섞어서 학습하지 말 것.**
> `6__replay.sh`도 `--robot.use_action_offset=false`로 바뀌었다(이중 보정 방지).

**depth를 안 켜더라도 이 수정은 반드시 들어가야 한다.**

### 폐기 완료 — 우리 depth 구현 전량 제거

- `lerobot_robot_piper/depth_utils.py` (turbo 컬러맵)
- `config_piper.py`의 `depth_min_m` / `depth_max_m` / `depth_scale` / `depth_raw_dir`
- `DEPTH_RAW_DIR` raw `.npy` 사이드카 — **완전히 무의미해짐.** 본 경로가 이미
  near-lossless인데 1.11 GB/분을 따로 쓸 이유가 없다
- `scripts/tools/test_depth_mock.py` — 삭제 (컬러맵 경로 전용 테스트였음)

결과적으로 **upstream 대비 우리 브랜치의 코드 차이는 effort/안전 컷오프뿐이다.**
