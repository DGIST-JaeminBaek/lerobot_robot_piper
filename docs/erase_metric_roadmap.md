# 지우기 과제 — metric 기반 개선 로드맵

작성 2026-08-14. `erase_the_{circle,triangle,rectangle}` 과제의 성공률을 올리기 위한
계획. 잉크 잔량 metric을 축으로 삼는다.

문제의식: **"다 지웠는지 판단"이 안 되는 게 아니라 "잘 지웠는지 잴 자(尺)"가 없었다.**
metric 없이는 어떤 개선도 개선인지 증명할 수 없다. 그래서 metric부터 만들고,
그 위에 나머지를 쌓는다.

---

## 1. 현재 도구

| 파일 | 역할 | 상태 |
|---|---|---|
| `scripts/tools/ink_metric.py` | 도형 자동 검출·분류 + 잉크 잔량 측정 (판정·QC용) | 검증 완료 |
| `ink_metric.dense_progress()` | 접촉 중에도 쓰는 조밀한 진행도 (곡선 전용) | 구현 완료, 미사용 |
| `scripts/tools/make_done_labels.py` | done 라벨 경계 + QC 제외 목록 sidecar 생성 | 검증 완료 |
| `scripts/tools/erase_check.py` | 추론 시 성공 판정 + check-and-retry 골격 | 오프라인 검증 완료 |
| `scripts/tools/wrist_ink_probe.py` | (검증 A 기록용) 손목 카메라 잉크 신호 확인 | **가설 기각됨** |

전부 `--selftest` 내장. 데이터셋 원본은 수정하지 않고 sidecar(`done_labels.json`)로만 관리한다.

## 2. 확립된 사실 (0802/0804/0805, 120 에피소드 실측)

### metric 성능
- 도형 검출·분류 **119/120**
- target `erased_frac` 평균 **0.987** vs distractor 평균 **0.009** — **분리도 110배**
- 노이즈 플로어: distractor p95 **0.037**, 최대 0.097
- 성공 판정: `target_erased ≥ 0.9 AND max_distractor_erased ≤ 0.10`
- QC 결과: **사용 115 / 제외 5** (target 미완 4, 오분류 1)

### 데이터의 시간 구조 — 이게 설계를 좌우한다
```
접근·파지 27%  |  접촉·지우기 51% (≈10.7초)  |  완료 후 유휴 22% (≈4.7초)
```
- 진행도는 **시간에 비례하지 않는다**: 에피소드 50% 지점에서 물리적으로는 1%만 지워져 있고,
  75% 지점의 표준편차가 0.47(사실상 이분포)
- 완료 시점 중앙값은 에피소드 길이의 **80%** — 뒤 20%는 다 지운 뒤 그냥 움직이는 구간
- 에피소드 길이 중앙 ~720 frame (30fps)

### 세팅상의 사실
- 도형은 매 에피소드 **손으로 다시 그린다** → 위치·종류가 매번 다름. 고정 ROI 불가
- **항상 target + distractor가 같이 보드에 있다** → 언어를 안 읽으면 원리적으로 못 푸는 구조
- 가림 프레임에서도 도형 면적의 **69%는 보인다** (지우개 블록 23%, 팔 8%)

## 3. 조합별 진행 계획

4부에서 제안한 조합들의 현재 상태.

### 조합 1 — progress head (ProgVLA 응용)

**상태: 조건부 재개.** 한 번 접었다가 `dense_progress()` 구현으로 되살아났다.

ProgVLA는 progress 타깃을 순수 시간 기반(`r_t = max(0, 1−(T−t)/T_M)`)으로 잡고, 논문 스스로
"과제 의미와 무관하다"고 명시한다. 우리 데이터에서 이 가정은 **틀린다**(위 §2 참고).
[Progress Reward 서베이](https://arxiv.org/html/2607.21655)도 "진행도가 시간에 따라 매끄럽게
증가한다는 가정"을 주요 실패 모드로 지목한다.

**우리 안**: 시간 대신 물리량. 그리고 구간별로 다른 신호를 쓴다.
```
phase 1 (접근·파지)   progress = 지우개까지의 EEF 거리 기반 (state에서 계산)
phase 2 (접촉·지우기) progress = dense_progress() 기반 잉크 밀도
phase 3 (완료 후)     progress = 1, done = 1
```
phase 경계는 사람이 안 붙여도 된다 — **그리퍼 상태 + 가림 플래그**로 자동으로 나온다.

**loss**: ProgVLA의 V/Q head까지 다 붙이지 않는다(우리 데이터 규모에 과함).
```
ℒ = ℓ_action + λ_P · MSE(progress) + λ_D · BCE(done),  λ = 0.1부터
```
가중치 재조정(`w_A,t · w_S,t`)은 나중에 — 성능 향상이 어디서 오는지 분리 검증이 가능해야 한다.

**선행 조건**: `dense_progress()`가 실제 학습 신호로 쓸 만한지 확인 (아래 T2).

---

### 조합 2 — done head (VLAC 응용)

**상태: 라벨 생성 완료. 학습 대기.**

VLAC의 라벨링 규칙을 따르되 시간 비율 대신 잉크 잔량을 쓴다. VLAC은 "완료 80% 이전 → 0,
95% 이후 → 1, **중간은 라벨 없음**"으로 애매 구간을 비운다. 억지로 0/1을 매기면 경계에서
모델이 흔들리기 때문이다.

우리 규칙 (`make_done_labels.py`):
```
erased < 0.5           -> done = 0
0.5 <= erased < 0.9    -> 라벨 없음
erased >= 0.9          -> done = 1
팔이 가린 프레임        -> 라벨 없음   ← 이게 중요
```
마지막 규칙: 지우는 동안 done=0을 박으면 "이미 다 지웠는데 아직 아니다"를 가르치게 된다.

**핵심 이득 — 유휴 구간 22%의 재활용.** 에피소드당 4.7초, 총 **17,159 프레임(약 9.5분)** 이
"이미 다 지운 상태"다. 버리는 대신 done=1 학습 데이터로 쓴다. **추가 녹화 0.**

산출물: `done_labels.json` (레포 루트). 학습 코드에서:
```python
from make_done_labels import load_labels
done = load_labels(entry)   # 프레임별 0 / 1 / -1(라벨 없음)
```

### 조합 3 — 리커버리 데이터

**상태: 녹화 필요. 우선순위 높음.**

현재 데이터가 담고 있는 보드 상태는 두 가지뿐이다: **완전한 도형**과 **완전히 깨끗한 보드**.
모든 시연이 완전히 그려진 도형에서 시작하기 때문이다.

그런데 실제 실패는 그 **사이**에서 일어난다. QC로 걸린 4건이 전부
"부분적으로 지워진 채 끝남"(erased 0.24 / 0.67 / 0.76 / 0.79)이다.

**처방**: 도형을 60~80% 지운 상태에서 시작하는 짧은 시연 20~30개 (각 5~8초).
접근·파지 구간이 없으므로 **거의 전부가 접촉·지우기 구간**이다 — 기존 데이터는 51%만 그렇다.
20 에피소드로 기존 40 에피소드분의 "지우기 동작"을 추가하는 셈.

서베이도 평가·학습이 "단조로운 시연을 넘어 실패·되돌림·정체·리커버리"를 다뤄야 한다고 권고한다.

**조합 5(retry)와 짝을 이룬다** — retry 2회차가 만드는 상황이 정확히 이 상태이므로,
정책이 그 상황을 본 적이 있어야 한다.

---

### 조합 4 — 카메라 ablation

**상태: 우선순위 하향.** 근거 하나가 무너졌다.

원래 기대: "top이 지우는 동안 가려지니 wrist가 메워줄 것" → **검증 A에서 기각**
(§5 참고). 게다가 top 카메라 자체의 가림 문제는 `dense_progress()`로 상당 부분 해결됐다.

남은 근거는 "접촉 작업이니 근접 시야가 유리할 것"이라는 약한 가설뿐이다. ablation 자체는
여전히 할 가치가 있지만(top-only / wrist-only / both × seed 3), 조합 2·3 뒤로 미룬다.

---

### 조합 5 — 추론 시 check-and-retry (신규, 최우선)

**상태: 구현·오프라인 검증 완료. 랩 PC 연결만 남음.**

논리: 잉크 metric은 접촉 중엔 못 쓰지만 **팔이 park로 빠진 상태에서는 완벽하다.**
정책은 한 시도가 끝나면 반드시 팔을 뺀다 → **매 시도 끝마다 정답을 알 수 있다.**

```
정책 실행 → 팔 park → 잉크 측정
   ├ target erased ≥ 0.9 AND distractor ≤ 0.10  → 성공, 종료
   └ 아니면                                      → 같은 명령 재실행 (최대 N회)
```

1회 성공률이 p면 3회 시도로 `1−(1−p)³`. p=0.5여도 87%. **모델을 전혀 안 건드린다.**
이 분야 벤치마크들이 애초에 "2회/3회/5회 wipe 안에 성공"으로 지표를 정의하므로,
재시도는 유리하게 잡은 셈법이 아니라 이 과제의 표준 프레이밍이다.

**검증**: 에피소드의 첫/마지막 프레임 2장만으로 판정 → 전체 영상 기반 판정과
**119/119 (100%) 일치**.

연결 방법:
```python
from erase_check import EraseChecker, retry_loop
history = retry_loop(EraseChecker(), grab_top_frame, run_policy_once, "circle", max_attempts=3)
```
`erase_check.py`는 **판정만 한다.** 로봇 제어는 `run_attempt` 콜백이 담당한다.

### 조합 6 — 물리적 개선 (신규, 비용 최소)

**상태: 다음 녹화 세션에 적용.**

- **ArUco 마커 4개를 보드 모서리에 부착**. A4 인쇄물이면 충분한데 세 가지가 풀린다:
  1. 휴대폰 등 추가 카메라를 아무 데나 놔도 homography로 정면 정규화 가능
  2. `DEFAULT_BOARD` 하드코딩이 사라짐 (지금은 카메라를 조금만 옮겨도 ROI 재설정)
  3. 손목 카메라 시점 정규화 → 검증 A 실패 원인이 제거될 가능성
  **단, 소급 적용 불가.** 기존 120 에피소드는 그대로다.
- **굵은 마커 사용** — 오분류 3건이 전부 흐린 선 때문이었다. 노이즈 플로어도 내려간다
- **보드 조명 균일화** — 가림 오탐의 주범이 팔 그림자다
- **휴대폰 판정 카메라**를 팔 접근 반대편에 배치. 단 **평가·감독용으로만**.
  정책 입력에 넣으려면 관측 공간이 바뀌어 120 에피소드를 다시 찍어야 한다

## 4. 실행 순서

```
[로컬, 완료]
  ✅ 잉크 metric + QC          → 사용 115 / 제외 5
  ✅ done 라벨 생성            → done=1 17,159 프레임
  ✅ retry 판정기 + 오프라인 검증 → 119/119 일치
  ✅ dense_progress 구현

[랩 PC — 다음 세션]
  T1. 조합 5 실측: 1회 vs 3회 성공률          ← 첫 성과 숫자, 재학습 0
  T2. dense_progress를 실제 롤아웃에 적용해 신호 품질 확인  ← 조합 1의 가부 결정
  T3. T0 언어 조건화 진단 (instruction 바꿔가며 20회)

[다음 녹화 세션]
  조합 6 (ArUco, 굵은 마커, 조명) + 조합 3 (리커버리 시연 20~30개)

[학습 — seed 3개씩]
  baseline vs +done head vs +done+리커버리     ← 조합 2·3
  progress head                                ← 조합 1 (T2 결과에 따라)
  top / wrist / both                           ← 조합 4
```

### T3 (언어 조건화 진단)을 빼먹지 말 것
데이터가 항상 target+distractor를 같이 담고 있으므로, 같은 보드 상태에 instruction만
바꿔서 롤아웃하면 된다. **별도 데이터 수집 불필요.** instruction을 바꿔도 같은 도형을
지우면 언어를 무시하고 있다는 뜻이고, 그러면 조합 1~3보다 언어 조건화가 먼저다.

서베이도 평가 항목으로 "**counterfactual instruction을 통한 task grounding**"을 명시한다.

## 5. 실패로 판명난 것 (재시도 방지)

### 검증 A — 손목 카메라로 잉크 측정: **기각**
3가지 방식 전부 무신호. 원인은 **시점 변화가 잉크 변화를 압도**하는 것.
top 카메라는 고정이라 "같은 픽셀의 밝기 변화 = 잉크 변화"가 성립하지만, 손목 카메라는
프레임마다 보는 장면 자체가 달라진다.

| 방식 | 결과 |
|---|---|
| 전체 프레임 dark+저채도 | 가림 중 0.069 / 비가림 0.062 — 신호 없음 |
| 상단 40% crop | 0.0318 / 0.0314 — 신호 없음 (도형이 crop 아래로 잘림) |
| 시간축 정적 마스크로 그리퍼 제거 | 0.75~0.81배 — **방향이 반대** |

되살리려면 조합 6의 ArUco 시점 정규화가 선행돼야 한다.

### dense_progress를 판정에 사용: **금지**
밀도 추정을 `erased_frac` 계산에 쓰면 분모(가시 픽셀 수)가 흔들려
**distractor 노이즈가 0.009 → 0.195로 폭증**한다(분리도 110배 → 5배).
진행도 곡선 전용. 코드 docstring에도 명시돼 있다.

### envelope(running-min)으로 판정: **폐기**
중간에 스쳐간 그림자 같은 일시적 저점을 그대로 붙잡는다.
"처음/마지막 유효 관측값"으로 바꿔서 distractor 노이즈 0.044 → 0.009, 분리도 22배 → 110배.
envelope은 진행도 곡선·`frames_to_90pct` 용으로만 남겼다.

## 6. 도구 구현상 주의점

실제로 다 버그였던 것들. 코드 수정 시 깨지 말 것 (전부 selftest로 방어돼 있다).

1. **채도 필터는 contour 병합 "전에"** — 나중에 하면 나무 지우개 블록이 옆 도형과
   한 덩어리로 묶여 bbox와 잉크 측정이 오염된다
2. **같은 종류 도형이 여러 개일 때 dict 키 충돌** — 시계열이 이어붙어
   `frames_to_90pct`가 영상 길이를 넘는 값이 나온다. 키를 `circle#0`, `circle#1`로 분리
3. **손그림은 획이 끊겨 contour가 조각난다** — bbox 근접(30px) 병합 후에 분류해야
   삼각형을 원으로 오분류하지 않는다
4. **모서리 둥근 손그림 사각형**은 extent가 원(0.785)과 겹친다 → hull 꼭짓점 수로 tie-break
5. **PAD를 붙일 때 프레임 밖으로 나가면** 빈 crop이 되어 cvtColor가 죽는다
